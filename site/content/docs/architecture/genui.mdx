GenUI is Macaron's headline feature: the model doesn't just describe a UI, it **writes TSX that renders live** in the conversation. Two halves make this work — a server-side tool the model calls, and a browser-side renderer that compiles and mounts the streamed code.

## The `render_ui` Tool

`server/src/lib/macaron-render-tool.ts` is the shared handler behind the `render_ui` MCP tool. It is used by **both** engines from one implementation:

<Cards>
  <Card title="Claude side">
    Exposed in-process via the Agent SDK's `createSdkMcpServer` — the tool lives inside the server.
  </Card>
  <Card title="Codex side">
    Exposed by a standalone stdio MCP server (`macaron-mcp-stdio.ts`) injected into each Codex turn, so `render_ui` is available on the Codex path too — **when running from a source or plugin install** (see the packaging note below).
  </Card>
</Cards>

Both surfaces return an **identical `tool_result` shape**, so the model self-corrects the same way regardless of engine. Before returning, the handler runs `checkGenUI` — a TypeScript diagnose pass over the submitted module — and flips `ok: false` when the code has type errors, so the model gets actionable feedback instead of a silent broken preview.

<Callout type="warn" title="Availability depends on the install form">
  This describes the retained source application. Its TypeScript diagnostics and runtime share the six-component UI4A contract. The unified `macaron-artifacts` distribution has its own harness and UI4A pipeline; see [Packaging](/docs/architecture/packaging).
</Callout>

<Callout type="info" title="UI changes preview first — by convention">
  The tool's server-level instructions ask the model to treat a preview as the deliverable for a UI-change turn: render a `render_ui` preview of the *after* state (ending in Apply / Tweak / Discard buttons) and stop, only editing files once the user clicks Apply. This is a **prompt policy**, not a server-enforced edit gate — the runtime does not block file writes on a prior preview, so it holds only as far as the model follows the instruction.
</Callout>

## The Live Renderer

On the browser side, `web/src/components/GenuiRenderer.tsx` connects the host import map to published `partial-react` and the shared frame-delivery implementation. It tolerates **incomplete** source, so each streamed chunk can render without waiting for the full module. The host shares the unified app's six lightweight UI4A components, uses UnoCSS `presetWind4` for utilities, and exposes Headless UI and Recharts directly for additional controls and charts.

<Steps>
<Step>
### Receive streaming code

`GenuiPreview` passes the accumulating `code` and a `streaming` flag straight through. While `streaming` is true it uses `flushMode="immediate"` and preserves component state across updates, so the preview morphs smoothly as tokens arrive.
</Step>
<Step>
### Compile the TSX

`createTsxCompiler` from `partial-react/compiler` transpiles the (possibly partial) module. Transform/parse errors mid-stream are transient — the renderer swallows them because the next chunk usually completes the syntax.
</Step>
<Step>
### Resolve imports

An import-map resolver maps bare specifiers (`react`, `$ui4a/ui`, `@headlessui/react`, `recharts`, `lucide-react`, and `motion/react`) to locally served shim modules. `$macaron/ui` aliases the same six UI4A exports. The host also installs a native import map so React externalized by the `esm.sh` fallback resolves to the page's own instance.
</Step>
<Step>
### Mount and cross-fade

The compiled module is mounted. In-place updates just re-render the live tree, but when the renderer has to **rebuild** (e.g. the import map changed and the old root is torn down) it holds a snapshot of the old DOM and cross-fades (~200 ms) to the new tree so the swap doesn't flash. Streaming token updates are not each a cross-fade — only the rebuild path is.
</Step>
</Steps>

## The Import Shims

`web/public/genui-shim/*.mjs` connects generated imports to the host's React, UI4A, Headless UI, Recharts, Lucide, Motion, and chat modules. A model-authored `import { Card } from '$ui4a/ui'` resolves to the shared lightweight component implementation.

The component contract is deliberately small:

| Export | Use |
| --- | --- |
| `Button` | Native button props, `primary` / `secondary` / `ghost` / `danger` variants, and `sm` / `md` sizes |
| `Field` | Native input props with a required `label` and optional `hint` |
| `Card` | A framed div; compose headings and body content with native HTML |
| `Badge` | An inline span for short status text |
| `Tabs` | Headless UI tabs from `items: { id, label, children }[]`, with optional `value` and `onChange` |
| `Disclosure` | Headless UI disclosure from `title`, `children`, and optional `defaultOpen` |

Use native HTML and Wind4 utilities for layout, lists, tables, and metrics. Shiki supplies semantic colors to both the application and generated surfaces. Additional interactive controls come directly from `@headlessui/react`; charts come directly from `recharts` with an explicit container height.

The retained host's chat actions remain `sendUserMessage` and `useAutoSend` from `$macaron/chat`. The unified app's scoped state and file capabilities are documented by its generated UI4A skill; they are not legacy chat-bridge APIs.

## The `genui-builder` Skill

The bundled **`genui-builder`** skill (`skills/genui-builder/SKILL.md`) teaches the host's six-component contract and streaming authoring rules. It prefers the `render_ui` MCP tool when exposed. A pinned `@genui/cli` (`bunx genui@…`) remains available for standalone export, but its separate module registry does not validate this host's capabilities.
