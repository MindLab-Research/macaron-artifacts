The front end (`web/`) is a Vite + React SPA. It has no server-side rendering — the Fastify server hands the browser the selected prebuilt HTML document and the app takes over from there with a hash router.

## Harness Entries, One Build

`web/vite.config.ts` declares the Claude, Codex, and Kimi entries in one build, so their SPA bundles share asset chunks:

```ts
input: {
  main: path.resolve(__dirname, 'index.html'),   // Claude UI
  codex: path.resolve(__dirname, 'codex.html'),  // Codex UI
  kimi: path.resolve(__dirname, 'kimi.html'),    // Kimi UI
}
```

The server picks which one is `/` at boot (see [Overview](/docs/architecture/overview)). In dev, Vite serves on `:5273` (`strictPort`) and proxies `/api` to the server on `:7878`.

<Callout title="One lightweight component contract">
  The retained web application shares the unified app's six `$ui4a/ui` components: Button, Field, Card, Badge, Tabs, and Disclosure. Native HTML and UnoCSS Wind4 utilities handle layout; additional controls and charts use `@headlessui/react` and `recharts` directly. `$macaron/ui` remains a compatibility alias for these same six exports. React and `partial-react` are deduplicated by Vite.
</Callout>

## Runtime Bootstrap

The three entries bootstrap GenUI differently. The **Claude** entry (`web/src/main.tsx`) stands up the whole GenUI runtime *before* the app renders — model-authored TSX previews are core to that UI, so the globals must exist up front. The **Codex** and **Kimi** entries (`web/src/codex/main.tsx`, `web/src/kimi/main.tsx`) stay chat-focused and **lazy-load** the GenUI runtime (`React.lazy` + `Suspense` in their chat views) only when a `render_ui` card needs to render.

The steps below describe the Claude bootstrap:

<Steps>
<Step>
### Expose React + Macaron globals

React, the JSX runtimes, ReactDOM, the six UI4A components, Headless UI, Recharts, Lucide, and `motion/react` are imported as namespaces and published to the page so streamed GenUI modules can resolve them without a bundler. Chat actions use the retained `$macaron/chat` bridge.
</Step>
<Step>
### Boot the UnoCSS runtime

`@unocss/runtime` with `presetWind4` + animations generates utility classes from the DOM at runtime. All three entries share one initialization path and Wind4's built-in reset, so lazily opening a generated UI never injects another reset over the application.
</Step>
<Step>
### Mount the hash router

`createHashRouter` wires the views — Dashboard, Workspace, Session, Settings, Analytics, and more — under the `App` shell.
</Step>
</Steps>

## Streaming a Turn

The client reads SSE with **`fetch` + a streaming body reader**, not `EventSource` (`web/src/lib/sse.ts`). That's deliberate: `EventSource` can't send a request body or custom headers, and turns are POSTs carrying the message + attachments. The reader parses the same `SessionStreamEvent` union the server publishes and dispatches into a live store that the views subscribe to.

## The Session Canvas

The Workspace view (`web/src/views/Workspace.tsx` + `web/src/lib/canvas.ts`) is a free-form canvas of session tiles rather than a list:

<Cards>
  <Card title="Pin & arrange">
    Pin a session with `+`; drag the grip to reposition, pull the bottom-right corner to resize, click a tile to focus.
  </Card>
  <Card title="Live tiles">
    Each tile tails its session over SSE, so thinking, tool calls, and GenUI previews update in place as a turn runs.
  </Card>
</Cards>

## Auth Gate

When the server arms a token (non-loopback bind), `web/src/components/AuthGate.tsx` intercepts the app: it reads the token from the `?token=` connect URL, stores it, and attaches it to every `/api` request. On loopback with no token, the gate is a no-op.
